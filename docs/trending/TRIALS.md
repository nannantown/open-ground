# Trials — how a candidate becomes part of OPEN GROUND, or gets reverted

> **Owner decision, 2026-09-22.** "Try it once, measure whether it really has an
> effect, and only then put it into the real thing. And if there is no effect, or
> something inconvenient happens, we should have a way to put it back."
>
> That is the method, written down so a later session runs it the same way.
> Candidates and their verdicts live in [OG-CANDIDATES.md](./OG-CANDIDATES.md);
> this file is the procedure and the running log.

## The method

Five steps, in order. The order is the point: the acceptance criterion is written
**before** the measurement, so a disappointing number cannot be reinterpreted
into a success afterwards.

1. **Write down what would count as working** — a number and a threshold, in the
   trial's section below, before running anything.
2. **Measure the baseline** with the instrument named in that section. If there is
   no instrument, building it is the trial's first half.
3. **Put the change behind an off-by-default switch.** Nothing that reaches the
   owner's machine changes until the switch is turned on. The switch is the
   revert path, and it is named in the section.
4. **Turn it on and measure again**, on the same subject where possible.
5. **Keep or revert, and record the number either way.** A reverted trial with a
   number is a result; a kept trial without one is a guess.

### What "measure" is allowed to mean here

This is a one-person product with a handful of cards a day, so most honest
answers are "we cannot tell yet". Two rules keep the numbers from lying:

- **N=1 proves nothing about fuel.** Cards differ in difficulty far more than a
  directive changes consumption, so a single before/after pair is noise. Either
  re-run the *same* card, or compare medians within one tier over enough cards
  and say how many.
- **A tool's own benchmark is a reason to trial it, never a result.** Every
  claimed figure in OG-CANDIDATES.md is marked *(their figure)*. A trial exists
  to replace one of those with ours, on this repository.

### The instruments OG already has

| Instrument | What it measures | Where |
|---|---|---|
| 7-day usage breakdown | fuel by role — worker / manager / supply / project | `claudeUsage.ts` + `swarmDeskLedger.ts` (0.11.117), shown in the Usage HUD |
| `scripts/swarm-token-audit.ts` | per-session token accounting | repo |
| Board card journal | what a worker did, and reworks | `~/.openground/projects/<uuid>/tasks.json` |
| `docs/trending/signals.json` | licence + cost of every candidate | regenerated by the cost scan |

The desk ledger shipped in 0.11.117, which is what makes the fuel trials
measurable at all — before it, worker and manager fuel were pooled into
"project".

## Can the swarm use these? — answered from the code, 2026-09-22

The owner asked directly. Three separate answers, because the swarm's surfaces
differ:

**1. As an MCP server inside a worker — no, and deliberately so.**
`swarmWorkerSdk.ts` passes `mcpServers: {}` with `strictMcpConfig: true`, and the
comment says why: *"`mcp__*` tools sit OUTSIDE the PreToolUse veto's tool set, so
a filesystem / shell / sql MCP would be an unguarded path straight past it. Load
none."* Any MCP in a worker reopens that path. This is a safety invariant, not a
preference — see `docs/SWARM_SAFETY_INVARIANTS.md`. Changing it would need the
veto extended to `mcp__*` first, as its own card.

**2. As a CLI the worker calls through Bash — yes, and this is the right shape.**
Bash *is* inside the veto's tool set, so a command-line query is policed exactly
like any other. `codebase-memory-mcp` ships precisely this: *"The ordinary `cli`
mode is intentionally separate: it runs one command locally and never starts or
connects to the coordination daemon, registers a daemon session, or starts
watchers/UI"* — e.g.
`codebase-memory-mcp cli search_graph '{"project":"og","name_pattern":".*Handler.*"}'`.
Same for `ocr` (open-code-review) in delegation mode.

**3. As a directive in the order text — yes, and it is the cheapest.**
`buildOrderInjection` in `swarmWorker.ts` already composes prefix + goal + prior
failure + tier directive + rules + language. A brevity clause or a "think in
code" clause is one more segment, already tier-aware since 0.11.117.

**⚠ One installer to keep away from the owner's Mac for now.**
`codebase-memory-mcp install` "auto-detects installed coding agents and configures
their documented MCP entries plus durable instructions, skills, and **lifecycle
hooks** where supported". OG's own PreToolUse guard is installed into
`~/.claude/settings.json` by `hooksInstall.ts`, under a "never touch
user-authored" ownership contract. Two installers writing the same hooks file is
the collision that contract exists to survive, and it has never been tested
against this one. Use the binary and its `cli` mode directly; do not run
`install` until the interaction is checked deliberately.

## Trial 1 — open-code-review in delegation mode

**Candidate:** `alibaba/open-code-review`, Apache-2.0, free in delegation mode
("your coding agent runs the review using its own LLM; no OCR API key required").
**Their claim:** higher precision and F1 than a general-purpose agent on the same
model at **~1/9 of the tokens**, on AACR-Bench.

**What would count as working**
- It produces findings on a real OG diff that a reviewer would call true, and
- its token consumption for that review is at most **half** of what OG's own
  adversarial review spends on the same diff.

Half, not a ninth: their number comes from 200 PRs in ten languages, and one
diff in one repository cannot reproduce it. Half is the threshold at which it is
worth wiring in; below that the wiring cost is not repaid.

**Switch / revert:** nothing in OG changes for this trial — `ocr` runs as an
external command against a diff. There is nothing to revert until it is wired
into the engine, which is a separate card.

### Result, 2026-09-22 — 採らない for the swarm's review. No quota spent.

Installed `@alibaba-group/open-code-review` v1.12.8 and ran it against a real OG
commit (`e3409b9`, the trial scaffolding itself).

**Delegation mode is real and free, as advertised.** `ocr delegate` needs no LLM
at all: `preview --from e3409b9~1 --to e3409b9` returned the file set in **722
bytes**, and `delegate rule <two files>` returned the review spec in **3,406
bytes**. No key, no provider configured, nothing billed.

**And that spec is why this stops here.** The rules are a generic JavaScript /
TypeScript / React checklist: spelling in identifiers, dead code, duplicate
logic, `var`, `==`, `any`, null checks, nested ternaries, React hook rules,
`useEffect` cleanup, inline styles, async error handling, XSS, `innerHTML`,
`eval`, prototype pollution. Every item is reasonable. **None of them is what
OG's adversarial review is for** — whether the guard was measured RED against
unmodified production, whether the completion gate is intact, whether the worker
committed before beating ready, whether the doc followed the code. A review
cannot return findings its spec never asks for, so the comparison the trial was
designed to make ("half the tokens for findings a reviewer would call true")
cannot even be set up: the two tools answer different questions.

**No way to supply our own checklist.** `ocr rules` only inspects the built-in
rule that applies to a path; `ocr config` covers providers, models and custom
endpoints. Nothing found in the CLI or the README accepts a project rule set. Had
it, the verdict would flip — a cheap harness for running OG's OWN checklist is
exactly what would be worth wiring in.

**A second finding, and the sharper one for this repository.** By default `ocr`
EXCLUDES test files (`default_path`) and markdown (`unsupported_ext`): of the
eight files in that commit it called four reviewable, dropping all four test
files and `TRIALS.md`. In OG the guards live in the tests and the canon lives in
the markdown, so the default configuration reviews the least load-bearing half of
an OG diff.

**Where their 1/9-token figure actually applies:** a general-purpose agent doing
*generic* review of *source* files. That is a real saving for that job. It is not
the job OG's swarm review does, so the figure does not transfer.

**Residual use, not pursued:** a cheap generic pre-filter over non-test source
before the real review. Small value next to the wiring, and it would need the
test/markdown exclusions inverted first.

## Trial 2 — codebase-memory-mcp, CLI mode

**Candidate:** `DeusData/codebase-memory-mcp`, MIT, no key, no runtime, no
service. **Their claim** (arXiv:2603.27277, 31 repositories): 83% answer quality,
**10× fewer tokens**, 2.1× fewer tool calls versus file-by-file exploration.

**What would count as working**
- A swarm-shaped question — "where does a worker's `readyToMerge` heartbeat get
  classified?" — answered correctly from `cli` queries alone, and
- the tokens spent reaching that answer at most **half** of the grep-and-read
  path on this repository.

**Switch / revert:** the worker-facing form is one optional segment in the order
text pointing at the `cli` command, off unless a flag is set. Reverting is
turning the flag off; no state is left behind because the index lives outside the
repository. The binary is removed with its own `uninstall`.

**Not in scope:** `install`, MCP wiring, the daemon, the watcher, the UI. Only
`cli`.

### Result, 2026-09-22 — PASSES, 3.06x. No quota spent, no key, no network.

Downloaded the release tarball directly (`codebase-memory-mcp-linux-amd64-portable.tar.gz`,
40 MB archive / 300 MB binary, v0.11.0) and ran it with `CBM_CACHE_DIR` pointed at
a scratch dir. **`install` was deliberately not used** — it writes MCP entries and
lifecycle hooks into agent configs, which is where OG's own guard lives.

**Indexing this repository: 11 seconds**, 13,227 nodes / 47,690 edges, no LLM.
It is honest about its own gaps in the same output: 39 files parsed partially and
6 unusable, each named, plus the excluded set.

**The question:** "where does a worker's `readyToMerge` heartbeat get classified?"

| Arm | What was fed to the model | Bytes |
|---|---|---:|
| A — `cli` | `search_graph` (535) + `get_code_snippet` (2,403) + `trace_path` (253) | **3,191** |
| B — grep-and-read | grep excluding tests (2,335) + 120 lines around the classifier (7,433) | **9,768** |

**3.06x less**, against a threshold of 2x. It answered correctly:
`classifyWorker` at `swarmOrchestrator.ts:1329-1359`, reached from
`runDispatchPass` → `monitorWorkers`, and it also surfaced
`docs/commander/02-worker-lifecycle.md` §5.2 — the chapter that documents that
function — because it indexes Markdown headings as nodes too.

**Why 3.06x is a FLOOR, not the real ratio.** Arm B was handed the answer in
advance: I already knew to read lines 1280-1400. An agent without the tool starts
from the grep, whose first eight hits in this repository are all test files, and
`swarmOrchestrator.ts` is **629 KB** — so the realistic unaided path reads more,
not less. The published 10x *(their figure)* is not contradicted by this; it is
simply not what a single hand-run query measures.

**Two frictions worth knowing before wiring it anywhere.** `get_code_snippet`
wants `qualified_name` while `trace_path` wants `function_name`, and
`trace_path`'s direction values are `inbound`/`outbound`/`both`, not
`callers`/`callees`. Both of my first attempts failed with a one-line error. Cheap
in bytes, one wasted turn each for an agent — so a worker-facing clause must spell
the exact call shape, not describe it.

**What "keep" means here — and the design the wiring has to take.** Measured
further the same day, because the obvious design does not survive contact:

| Measured | Value |
|---|---|
| Index of the main checkout | 10-11 s, 13,227 nodes, **39 MB** on disk |
| Index of a fresh `git worktree` of the same tree | 10 s, 13,229 nodes, **66 MB** |
| Project key | derived from the ABSOLUTE PATH — a worktree gets its own key (`tmp-…-wt-probe`), never the parent's |
| Two cache roots at once | refused: "a genuinely different root is rejected while any CBM process is active" (its own README) |

Read together those four rule out the design you would reach for first. OG's swarm
gives every worker its own worktree under
`~/.openground/projects/<uuid>/worktrees/`, so "each worker indexes its own
worktree" means **10 s and ~50 MB per dispatch**, and the obvious fix — give each
worker its own `CBM_CACHE_DIR` so the index dies with the worktree — is refused
outright while another worker is running. Per-worktree indexing plus a shared
cache would leave tens of megabytes behind per card.

### Re-measured 2026-09-22, after the owner asked why a binary is needed at all — VERDICT REVERSED

The question was fair and the answer is that it is not needed. Two faults in the
measurement above, both mine:

**Fault 1 — the baseline was wrong.** Arm B is "grep blindly and read", but
`CLAUDE.md`'s first instruction is to read `docs/MAP.md` before exploring. That is
the baseline this repository actually has, and it was never measured.

**Fault 2 — the intake is a list of PRODUCTS, so every answer it offers is a
product.** "We need an index" got read as "we need their index". Nothing about the
goal requires a compiled program.

Same question, four arms, all measured:

| Arm | Bytes into context | What it costs to have |
|---|---:|---|
| A — `codebase-memory-mcp cli`, 3 queries | 3,191 | 286 MB binary + 39 MB index + an install that must route around its own installer |
| B — blind grep-and-read | 9,768 | nothing |
| C — **MAP.md first, as `CLAUDE.md` prescribes** | **9,653** | nothing (already written) |
| D — **a symbol index built by one `grep`** | **2,261** | nothing: 30 ms, one 123 KB file, 2,386 entries |

**Arm C is the more uncomfortable number.** Reading MAP.md first saved 115 bytes
out of 9,768 — nothing. MAP.md names FILES, not symbols: grepping it for this
topic returns four lines that point at `swarmOrchestrator.ts` and never mention
`classifyWorker`, so the 629 KB file still has to be searched. MAP.md is doing its
job (which area, which entry file, which pitfalls); it was never a symbol index,
and this is the first measurement showing where that boundary sits.

**Arm D beats the binary.** One `grep -rnoE "^export (const|function|…) name"`
over `src server scripts electron` produces `name → file:line` for 2,386 exports
in 30 ms. The lookup that answered the question cost **56 bytes** —
`src/lib/server/swarmOrchestrator.ts:1329|classifyWorker` — against the binary's
535, and the whole three-step path cost 2,261 bytes against 3,191. **1.41× less
than the 286 MB binary, 4.32× less than blind grep, with nothing installed.**

**What the binary genuinely does better, stated fairly:**
1. **Transitive callers.** `trace_path` returned `monitorWorkers` (hop 1) AND
   `runDispatchPass` (hop 2); grep returns the one direct call site. For
   blast-radius work that gap is real.
2. **Finding what you cannot name** — semantic search over the graph. Arm D needs
   you to know roughly what the symbol is called.
3. 162 languages, HTTP route extraction, cross-service links. OG is one
   TypeScript repository with its routes already listed in one file, so none of
   this applies here.

Neither (1) nor (2) is OG's common case, and both have cheap fallbacks (one more
grep hop; a plain-text search).

**Verdict: do NOT install the binary.** The 3.06× above stands as measured, but
it was measured against the wrong opponent. Against a 30 ms grep it loses. Trial
2's outcome is therefore: *the goal is worth pursuing, this implementation is
not.* The next card is arm D — a symbol index generated in-repo, offered to the
worker as one order-text clause behind a flag, with nothing to install on any
machine — and it now has a number to beat (2,261 bytes) rather than a claim.

**The install runbook below is kept, not followed.** Every value in it is
verified, and it is the fallback if arm D ever proves insufficient (most likely
reason: transitive call graphs). Treat it as reference, not a step.

**So the design is: ONE index of the parent checkout, which the workers only
read.** A worker's worktree starts as a copy of the base, and the graph's job is
finding EXISTING seams — which is exactly the part that is identical. The only
thing it cannot see is the code the worker itself just wrote, which the worker
already knows. Workers index nothing, wait for nothing, and leave nothing.

Remaining pieces for that card, none of them guesswork any more:
1. Index the parent checkout once (boot-time or by hand), and re-index on demand.
2. A `codeGraph` trial flag whose clause tells the worker to run `list_projects`
   first and match its project by `root_path` — the key cannot be spelled in the
   clause, because it is a slug of an absolute path.
3. Gate it to `standard` / `design` / `ultra`. A `touch` card does not explore
   enough to repay anything.
4. The clause must spell the exact calls (`get_code_snippet` takes
   `qualified_name`; `trace_path` takes `function_name` and
   `direction: "inbound"`, where `"callers"` is rejected) and say "if the command
   is missing, carry on with grep" — so a machine without the binary loses
   nothing.
5. The binary on the owner's Mac, installed by hand from the release tarball and
   **never** via `install`.

*(Those five pieces describe the design IF this tool were adopted. Per the
re-measurement above it is not — they are kept because the reasoning behind each
one survives whatever provides the index.)*

#### Installing the binary on the owner's Mac — the verified steps

Every value below was checked against the live release on 2026-09-22. **Do not
run `install.sh`, and do not run the binary's own `install` subcommand** (both
are shipped inside the tarball): they write MCP entries and lifecycle hooks into
agent configuration files, and `~/.claude/settings.json` is where OG's own
PreToolUse guard lives under a "never touch user-authored" contract. Everything
here avoids that path entirely — which also means the quarantine strip and
ad-hoc signing that `install.sh` does at its lines 317-325 have to be done by
hand, and step 4 is exactly those two commands.

```bash
# 1. a place for it that needs no sudo, and download (~39 MB)
mkdir -p ~/.local/bin ~/cbm-dl && cd ~/cbm-dl
curl -fL -O https://github.com/DeusData/codebase-memory-mcp/releases/latest/download/codebase-memory-mcp-darwin-arm64.tar.gz

# 2. verify against the release's own checksums (never a hash pasted from chat)
curl -fL -O https://github.com/DeusData/codebase-memory-mcp/releases/latest/download/checksums.txt
shasum -a 256 -c checksums.txt --ignore-missing
#    expect: codebase-memory-mcp-darwin-arm64.tar.gz: OK
#    the hash seen on 2026-09-22 was
#    4dee7f38b63740e6751d7a7ed7eb10291c1f2a3ea2415f599dc68370ca0a2d18

# 3. unpack and move ONLY the binary (the tarball also carries an install.sh —
#    leave it behind on purpose)
tar xzf codebase-memory-mcp-darwin-arm64.tar.gz
mv codebase-memory-mcp ~/.local/bin/

# 4. macOS gatekeeper: strip quarantine + ad-hoc sign (install.sh's own two lines)
xattr -d com.apple.quarantine ~/.local/bin/codebase-memory-mcp 2>/dev/null || true
codesign --sign - --force ~/.local/bin/codebase-memory-mcp

# 5. on the login-shell PATH, because that is the PATH OG hands its workers
#    (electron/main.js resolves it with `zsh -lic` before forking the server)
grep -q '.local/bin' ~/.zshrc || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc

# 6. check, in a NEW terminal
which codebase-memory-mcp && codebase-memory-mcp --version   # expect 0.11.0 or later
```

**What it puts on disk.** The binary itself is large (the Linux build measured
286 MB; expect the same order on macOS — `ls -lh` after step 3). Indexes and
config go to `~/.cache/codebase-memory-mcp`, **39 MB** for this repository. Its
README states it makes no network request of its own accord and collects no
telemetry.

**Indexing this repo, once:**

```bash
codebase-memory-mcp cli index_repository '{"repo_path":"/absolute/path/to/PMmap"}'
codebase-memory-mcp cli list_projects '{}'        # note the project key it prints
```

**Removing it, completely:** `rm ~/.local/bin/codebase-memory-mcp`,
`rm -rf ~/.cache/codebase-memory-mcp`, and drop the `~/.zshrc` line. Nothing else
was touched — which is the whole reason for avoiding `install`.

## Trial 3 — archify into a Canvas mock element

**Candidate:** `tt-a1i/archify`, MIT, free; optional update ping disabled with
`ARCHIFY_UPDATE_CHECK_DISABLED=1`.

**What would count as working**
- One generated HTML diagram of the swarm dispatch pass renders inside an OG
  Canvas mock element without new rendering work, and
- a reader who does not know the engine can say what happens to a stalled worker
  from the diagram alone — something `docs/commander/01-engine-core.md` prose
  currently takes several screens to convey.

This one is a judgement, not a number, and says so. The measurable half is only
"does it render in the existing surface".

**Switch / revert:** none needed — the output is one HTML file pasted into a
Canvas element, deleted like any other element. OG code is untouched.

### Result, 2026-09-22 — PASSES, in the real Canvas. No quota spent.

An earlier note here said this needed the owner's Mac. That was wrong, and worth
recording as an error: this container has Chromium and Playwright, OG boots from
`playwright.config.ts`'s own webServer (Hono in prod mode, isolated HOME, port
47876), and the repo already has an e2e harness that seeds a Canvas over the API.
The only genuinely machine-bound half was *generating* a diagram with a `claude`
session — and it turned out not to be needed, because **archify ships its own
generated example** (`examples/web-app.html`, 811 KB, `generator: archify
2.17.0-dev.1`). Using the tool's own artefact tests the real question — does
archify's OUTPUT render in OG's surface — without asking a model for anything.

**The real question was the nesting.** Archify emits a COMPLETE html document;
OG's mock element inlines its source as the `<body>` contents
(`mockSrcdoc.ts` `HTML_TEMPLATE`). Two arms were built: **A** the document
exactly as archify emits it, **B** only its body plus the `<head>` styles and
scripts hoisted in.

| Arm | svg area painted | DOM nodes | Console errors |
|---|---:|---:|---:|
| A — archify's document as-is | 470,885 px² | 675 | **0** |
| B — body + hoisted head assets | 470,885 px² | 671 | **0** |

**Identical.** Arm B's extraction is unnecessary: the nested document renders as
the tool ships it. One concern turned out to be unfounded — archify sets
`data-theme` on `<html>`, which a nested document loses, but its own boot script
re-sets it on `document.documentElement` at runtime, so the theme survives.

**Then the same artefact in the actual product**, seeded as a `mock` element
(`framework: 'html'`, 1280×820) into a real project's Canvas and driven through
the UI: the element renders with its chrome ("ARCHIFY — SAMPLE WEB APP", `html`
badge), appears in the Pages/Layers panel, and the sandboxed iframe reports the
**same 470,885 px²** as the standalone run. Screenshots:
[in the Canvas](./assets/trial3-archify-in-canvas.png) ·
[the srcdoc alone](./assets/trial3-archify-srcdoc.png).

**A measurement mistake worth keeping.** The first in-Canvas run failed its own
assertion at 9,432 px² while the screenshot showed a perfect diagram: the probe
scanned `page.frames()` by url/name and measured the Canvas toolbar's own icons
instead of the mock's frame. Resolving the frame through the element
(`elementHandle().contentFrame()`) gave 470,885. A geometry assertion is only as
good as the frame it runs in — and the screenshot is what caught it.

**Verdict: 試す → keep.** No OG change is needed at all: paste archify's HTML into
a mock element and it works. The temporary spec and its 811 KB fixture were
deleted after the measurement; the screenshots are the record.

**What is still unmeasured:** the second half of the acceptance criterion — "a
reader who does not know the engine can say what happens to a stalled worker
from the diagram alone". That needs a diagram OF THIS ENGINE, which needs one
`claude` session with the skill installed
(`ARCHIFY_UPDATE_CHECK_DISABLED=1 npx skills add tt-a1i/archify -g`), and it is a
judgement, not a number. Rendering is proven; usefulness is not.

## Trial 4 — the two order-text directives

**Candidates:** the brevity idea from `JuliusBrussee/caveman` (MIT skill) and the
"think in code" idea from `mksglu/context-mode` (Elastic-2.0 — **the idea only,
no code taken**). Both become one clause each in `buildOrderInjection`.

**What would count as working**
- Median worker fuel per card, within one tier, drops by **≥15%** across at
  least **six** cards per arm, and
- rework count and escalation count do not rise.

Two arms, measured separately, because the evidence for them differs: "think in
code" changes how a worker *gathers* (low risk), brevity changes how it *writes*
(caveman's cited JetBrains/Adobe results say quality holds; context-mode cites
benchmark degradation from aggressive brevity, so this arm is the one that can
lose).

**Scope guard:** brevity applies to `touch` and `standard` tiers only. `design`
and `ultra` exist because review depth is the point there.

**Switch / revert:** one off-by-default flag per arm, read at the spawn site and
threaded into `buildOrderInjection` exactly as `tier` already is. Flag off ⇒ the
order text is byte-identical to today, which is the property to pin with a test.

**Turning it on, 2026-09-22: a Settings switch, not a `curl` command.** The
first instruction handed to the owner was a `curl -X POST /api/settings`
one-liner; they asked for something clearer, correctly. Settings → 詳細設定 →
「Swarm worker の試験(計測中)」 now carries the toggle, hidden unless Swarm is on
for that user (a switch that changes nothing visible is worse than an absent
one). Shipped in 0.11.119. Verified in the running app, not just in unit tests —
[screenshot](./assets/trial4-switch-in-settings.png) — by booting OG through the
e2e harness, opening Settings in Japanese, pressing the switch and reading the
value back from `GET /api/settings`.

Two things that verification caught which the unit tests had not:
- **OFF is stored as the key being ABSENT**, not as `false` —
  `normalizeWorkerTrials` keeps only `=== true`. The first in-app assertion
  expected `false` and failed against correct behaviour.
- The switch's displayed state is driven by the **re-seed on open**, not by the
  `useState` initializer: replacing the initializer with `false` left every test
  green, while breaking the re-seed turned one red. A comment at the site now
  says which line is load-bearing, so the next reader does not "simplify" the
  wrong one.

**Status 2026-09-22: built, off, and waiting for cards.** `Settings.workerTrials`
(`{ brevity?, thinkInCode? }`) is implemented and every flag is off, so the order
text is byte-identical to before the trials existed — pinned by a test and
measured against eight mutants. Turning an arm on is a POST to `/api/settings`;
turning it off restores the previous text exactly.

**What the trial itself costs, measured (no quota):** each clause is ~120
characters, both together add **249 characters to a 3,532-character order text —
7.0%**, the same order of magnitude as one tier directive (135). So the input
cost of running the experiment is noise; whatever the arms do to consumption,
they are not paying for themselves in overhead.

The measurement cannot happen here: it needs six real cards per arm dispatched on
the owner's machine, read back from the 7-day usage breakdown. Enable ONE arm at a
time — `thinkInCode` first, since it is the low-risk one — and leave it for six
cards before looking.

#### If the owner says 「燃料の測定を始めて」 — start here

That exact Japanese phrase is the owner's way of asking for this trial to be
run, and it is written here verbatim so a `grep 燃料の測定` from a fresh session
in this repository lands on the procedure. (It was NOT findable on 2026-09-22:
「燃料の測定」 appeared nowhere, 「燃料」 only in a UI string file and one release
note, and neither `CLAUDE.md` nor `docs/MAP.md` mentioned any of it. A procedure
nobody can find is a procedure that gets re-invented.)

Related phrasings that mean the same request: 「燃料」「トークンの測定」「試験の計測」
「thinkInCode を測って」.

What to do, in order:

1. Check the switch's current state — `GET /api/settings` on `127.0.0.1:47776`,
   field `workerTrials.thinkInCode`. It must be OFF to start, because the
   baseline half comes first.
2. Take the first reading: `npx tsx scripts/fuel-mark.ts --label A-off --append <file>`.
   ⚠ This only works ON THE OWNER'S MACHINE — a cloud session cannot reach the
   app's loopback port at all.
3. Tell the owner to run six cards, and stop. Do not dispatch cards yourself:
   they are real work on real repositories and that is the owner's call.
4. After six: `--label B-off`, then turn the switch ON (Settings, or
   `POST /api/settings` with `{"workerTrials":{"thinkInCode":true}}`), then
   `--label C-on` immediately, six more cards, then `--label D-on`.
5. `npx tsx scripts/fuel-mark.ts --compare <file> --cards 6` twice — B−A and
   D−C — and read `perCard['swarm-worker']`. Heed `windowRisk`.
6. Write the numbers into the Log table at the bottom of this file, whichever
   way they came out, and turn the switch off if there was no effect.

#### The in-app protocol (0.11.120 onward, no terminal)

Until 0.11.120 the breakdown showed only a SHARE, and a share cannot be
subtracted — which is why the first instruction handed to the owner was
`npm run swarm:audit` in a terminal, inside an app that exists so a terminal is
not needed. Each row now carries its token count, so the whole measurement is
reading one number four times.

**Both arms have to be measured, and the baseline comes first.** An earlier
version of this note described only the switched-ON half, which would have
produced a number with nothing to compare it against.

| # | Do | Record |
|---|---|---|
| 1 | Switch **off**. Open the usage panel, find the `worker` row | `A` = its token figure |
| 2 | Run **6 cards** | — |
| 3 | Open the panel again | `B` |
| 4 | Switch **on** (Settings → 詳細設定) | — |
| 5 | Run **6 cards** | — |
| 6 | Open the panel again | `C` |

Baseline per card = `(B − A) / 6`. Trial per card = `(C − B) / 6`.

**Two traps in that arithmetic, both worth stating before the number is
believed:**
- **The window is 7 days and it MOVES.** If the twelve cards span more than a
  week, `A` is already ageing out of the window while the later cards are added,
  and the subtraction silently understates. Run the twelve inside a few days, or
  the comparison is not one.
- **Other work lands in the same row.** The `worker` row counts every swarm
  worker, so a card dispatched for something unrelated in between joins the
  total. Either keep the two blocks of six clean, or expect the difference to be
  noisy in the direction of "no effect".

If `(C − B)` is not clearly smaller than `(B − A)`, the honest reading is *no
effect measured* — switch it off and record the number. The one-shot test
already put the effect inside the noise (§Trial 5); this protocol exists to see
whether a many-turn worker behaves differently, not to confirm a hope.

## Trial 5 — the two order-text arms, measured against real `claude` runs

Run 2026-09-22 because the owner asked for both remaining items measured. This
is the first trial here that spent subscription quota: **15 `claude -p` runs,
$2.65 total**, reported by the CLI itself rather than estimated.

### Method, and two contaminations that had to be fixed first

Three questions, each naming a symbol and asking for its definition site and all
its call sites — a worker-shaped task. Same question, arms differing only by one
prepended clause. Two attempts were thrown away before the numbers below:

1. **Every `claude -p` joined the caller's session.** `CLAUDE_CODE_SESSION_ID` is
   set in this container's environment, so the second question answered "as
   already established" and the token counts included the whole parent
   conversation. Fixed by unsetting it and passing a fresh `--session-id`.
2. **The answers were in my own documents.** The first question set used
   `classifyWorker`, `buildMockSrcdoc` and `setUserSettings` — all three written
   into this very file and into OG-CANDIDATES.md earlier the same day, with their
   file and line. The agent could answer by grepping `docs/`, not the code. Fixed
   by picking symbols that appear in **no** markdown at all (`writeSession`,
   `readCanvasFile`, `__resetSdkSessionsForTests` — 85-104 mentions each in code,
   zero in docs), selected mechanically with `comm`.

Metric: the aggregate `usage` block, not `usage.iterations` — `iterations`
carries only the last message, which under-counted a 2-turn run by half.

### Result

| Arm | n | cost | input tokens | output tokens | turns |
|---|---:|---:|---:|---:|---:|
| off (baseline) | 6 | 0.1817 | 127,505 | 3,455 | 2.2 |
| `thinkInCode` 「開く前に絞る」 | 6 | **0.1679 (−7.6%)** | 116,631 (−8.5%) | 2,362 (−31.6%) | 2.0 (−7.7%) |
| `symbolLookup` 「定義だけ引く」 | 3 | 0.1834 (+0.9%) | **209,823 (+64.6%)** | 2,411 (−30.2%) | **3.7 (+69.2%)** |

**`symbolLookup` — REMOVED, by its own measurement.** Its pre-flight number was
real and irrelevant: a declaration-anchored grep returned 60-116 bytes where the
bare name returned 1,567-10,033 (26-104× less text). Run against a live agent it
made things **worse** — 69% more turns, 65% more input. The cause is visible in
its own transcript: the `^` anchor misses an **indented** definition (one test
file declares a local `writeSession`), so the agent spent extra turns discovering
that the grep had lied to it. The arm's code, flag, type and tests are deleted;
this paragraph is what remains.

**Two lessons worth more than the arm was.** First, **bytes of command output is
not tokens per task.** The fixed session overhead is ~60,000 tokens (system
prompt, CLAUDE.md, tool schemas); 7 KB of grep output is noise against it, which
is why the input tokens barely moved in the arm that was supposed to halve them.
Second, **a clause that is confidently wrong costs more than no clause** — the
agent pays to discover the error.

**`thinkInCode` — NOT PROVEN, direction favourable, keep the flag off.** −7.6% on
cost sits **inside the baseline's own 22% spread** (0.1650-0.2019 across six runs
of the same three questions), so it cannot be called a win. What points the same
way: it was cheaper in 5 of 6 paired runs, used 7.7% fewer turns, and wrote 31.6%
fewer output tokens.

⚠ **The output-token drop is NOT evidence for this clause.** `symbolLookup` cut
output by 30.2% as well, while being harmful on every other axis. Adding *any*
directive appears to make the model terser, so a 30% output reduction is what the
act of adding a clause buys, not what either technique buys.

**What would settle it, and it is the thing this test structurally cannot do.**
Every run here was 2-4 turns on a bounded question, where fixed overhead
dominates. A real swarm worker runs for many turns and exploration is a much
larger share of its total, which is exactly where the clause could pay. That
needs the six cards per arm on a live machine — the measurement this trial was
always going to hand back.
