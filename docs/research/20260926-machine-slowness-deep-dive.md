# パソコンが重い原因 — 第2弾の調査結果(2026-09-26 15:43〜16:11 実測)

調査のみ。何も消していない・設定もコードも変えていない。
【実測】= この時間帯に数えた数字。【推測】= 数字からの見立て(裏は取れていない)。

## ① 重さの原因の順位

1. **作業係のテストが同時に何本も走ること**【実測】
   - 忙しい時間帯(15:52〜16:00)と静かな時間帯(16:05〜16:11)を30秒おきに比べた:
     - ロード(順番待ちの仕事の数): 忙しい時 360〜720 / 静かな時 33〜50。頭脳は11個なので、忙しい時は1つの頭脳に30〜60個の仕事が並んでいた。
     - 動いているプログラムの数: 約940 → 最大約1,400(テストが一時的に約450本のプログラムを立ち上げる)。
     - メモリの空き: 忙しい時は 0.2〜0.5GB まで減り、スワップ(メモリが足りない分を保存領域に逃がすこと)が 1.4GB → 2.5GB に増えた(約1.1GB を書き出し)。静かな時はスワップが増えていない。
   - 小さな実験(同じテスト205ファイル・4,680件を、1人分だけ並列数を変えて走らせた):

     | 並列数 | かかった時間 | 使った頭脳の合計時間 | 走らせた時のまわりの混み具合 |
     |---|---|---|---|
     | 既定(10) | 196秒 | 350秒 | とても混んでいた(ロード 570) |
     | 3 | 215秒 | 306秒 | 混んでいた(ロード 180→45) |
     | 2 | 214秒 | 298秒 | やや空いていた(ロード 42→35) |
     | 既定(10)・2回目 | 143秒 | 343秒 | やや空いていた(ロード 35→44) |

     - 空いている時に1人で走らせるなら、既定(10)が一番速い(143秒。2〜3 だと約1.5倍の214秒)。
     - 混んでいる時は差が小さい(196秒 と 215秒 で約1割)。頭脳の取り合いで、並列を増やしてもほとんど速くならない。
     - 並列10のほうが頭脳を1割強余計に使う(350秒 と 300秒)。取り合いの手間の分。
     - 【推測】8人が同時に走らせると、1人10本 × 8人 = 最大80本 が頭脳11個を奪い合う。1人2〜3本に抑えれば16〜24本で、全体が仕上がる速さはほぼ同じまま、画面や会話の引っかかりは大きく減るはず。
2. **iPhone のシミュレーター(画面上の iPhone)が起動したままになっていること**【実測】
   - 「iPhone 17 Pro」が 15:43 の約55分前から起動中。中で約360本のプログラムが動き、メモリを約7GB 使っている(頭脳はほとんど使っていない・約3%)。
   - 【推測】iPhone アプリ系プロジェクトの作業係が確認用に立ち上げ、閉じずに残っている。
3. **Ollama(手元で動く AI)がメモリに載っていること**【実測】約1.3〜3GB(15:43 時点で起動から15分)。
4. **署名の確認係(trustd / ecosystemd / ecosystemanalyticsd)**【実測+推測】
   - 3つ合わせて、常に頭脳 約0.6〜1個分を使っている(ecosystemd は29日で合計149時間分 = 平均で頭脳0.2個分。trustd は7日で44時間分)。
   - 記録を見ると、やっているのは「プログラムの電子署名を確かめる」「Apple の公証が付いているか確かめる」だけ。
   - 【推測】新しいプログラムが立ち上がるたびに確認が走る。テストは git などの小さなプログラムを大量に立ち上げるので、1番の「テストの同時実行」の副作用。単独の原因ではない。
5. **保存容量の不足(空き 35GB・96%使用)**【推測: 今の遅さへの影響は小さい】
   - スワップは最大でも 2.5GB なので、今の空きで足りている。ただ、作業場所がもう少し増えると空きが危険な水準に近づく(下の内訳を参照)。

**OPEN GROUND と作業係が残しているもの**【実測】
- 作業場所 15個・合計 約3.7GB。すべて git に登録済みで、3日より古いものはない → 消し忘れは見つからなかった。登録されていない空の作業場所が1つ(8KB・影響なし)。

## ③ 改善案(効く順・作業係の人数は減らさない前提)

**オーナーがやること**
1. iPhone のシミュレーターを使っていない時は閉じる → メモリ約7GB が空く。忙しい時のスワップがほぼ無くなる見込み【推測】。
2. Ollama を使っていない時は終了する → メモリ 1〜3GB が空く。
3. 一度再起動する → テストの一時ファイル 1.9GB などが片付き、署名確認係もリセットされる。準備済みの OS 更新もここで入る可能性がある(時間がかかるかもしれない)。
4. 容量を空ける(効き目は「将来の予防」。今の速さはほとんど変わらない)。大きい順に: 使っていない古いシミュレーター(Xcode の設定 › Components。約73GB+端末26GB が対象になりうる)/ 使っていなければ Docker(37GB)/ 古い iPhone 用の部品(23GB)/ npm のキャッシュ(18GB)。どれを消すかはオーナー判断。

**アプリ側で直すこと**(別カードで。今回は何もしていない)
1. 作業係のテストの並列数に上限を付ける(1人あたり2〜3)。一番効く。実験では、混んでいる時の1回あたりの時間はほぼ同じ(+1割)、空いている時は約1.5倍になる。
2. パソコン全体で「全部のテスト」を同時に走らせる作業係の数を絞る(例: 同時に2人まで・残りは順番待ち)。1と組み合わせると、ロードの山がさらに低くなる。
3. テストが /tmp に残す一時ファイル(`openground-test-home` など)を、終わったら片付けるようにする。
4. 作業係が起動したシミュレーターを、カードが終わったら閉じるようにする(起動した作業係の確認が先)。

## 調べ方(技術メモ)
- 30秒おきの計測: `.scratch/sample.mjs`(sysctl vm.loadavg / vm.swapusage / vm_stat / ps。コミットしていない)。
- 実験: `npx vitest run src/lib/server --reporter=dot [--maxWorkers=N]`(vitest 4.1.7、run モードの既定 maxWorkers = 頭脳の数−1 = 10)。4回とも `sdkGuardHook.test.ts` の3件が赤。原因は、作業場所のパスが ~/.openground 配下にあると guard がフックの読み込み元を拒むこと。並列数とは関係ない(作業場所の場所で決まる既知の現象)。
- シミュレーターのメモリ: CoreSimulator 配下のプログラムについて `top -l 1` の MEM を合計した。

- 熱: `pmset -g therm`。`powermetrics` は管理者権限(sudo)が必要で、guard が止めるので使っていない。
- 容量: du / diskutil apfs list / tmutil listlocalsnapshots / xcrun simctl(サイズの集計だけ)。
