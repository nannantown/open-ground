# 並列オーダーと操舵 — 受付 / ライブ・ロスター / 方向で止める

> ステータス: **構想メモ（壁打ちの結晶）**。実装ブランチはまだ無い。
> カンバン（Board）作業と地続き。実装着手前に「未決の分岐」を詰めること。
> 関連: [ASSISTANT_DOCK_PLAN.md](./ASSISTANT_DOCK_PLAN.md)（常駐アシスタント＝受付の前身）

## 0. 出発点（痛み）

サイドバー（アシスタント・ドック）でエージェントを動かせるが、**会話が1本**。
複数タスクを頼むと直列で詰まる。掘り下げた結果、痛みの正体はこうだった：

- 痛みは「**遅い**」ではなく「**詰まる**」。
  命令する → 「動いています」と出る → **その待ち時間そのものが、次のやりたいことを生む**。
  なのに入口は塞がっていて、あふれた意図の行き場がない。
- ユーザーにとって**未実行の意図は"借金"**。メモ（インボックス）に逃がしても鳴り止まない。
  動き出して初めて鎮まる。→ **受け皿（passive queue）は解にならない。**
- 反射は2つ：湧いた次の意図は「**別の仕事＝並走させたい(2)**」か
  「**さっきの続き＝走ってる子に足したい(3)**」。1（ただ溜める）は選ばれなかった。

## 1. ねらい（Goal State）

**「あなたと話す者」と「作業する者」を引き剥がす。** 今のドックは話す相手＝働く相手が
同一なので、渡すと黙る（＝ドアが閉まる）。これを割る。

- **受付（前面・常時開）**: 受け取って後ろに流すだけ。**重い作業をしないから、塞がらない。**
  入口は永遠に開いている＝あなたを"待ち"にしない／"貯蔵庫"にしない。
- **ライブ・ロスター（盤面）**: 走っているタスクが**常に見えている**帯。
  各タスクは「いまどっちに向かっているか」を蒸留して脈打つ。
- **方向で操舵**: 意図・方向が常に読めるから、**やばかったら途中で止める・軌道修正できる**。

比喩の転換: **「秘書」をやめて「受付」にする。** 秘書は仕事を抱えるから話しかけると
「手が離せません」になる。受付は伝票を奥に回すだけだから、奥がどれだけ忙しくても
カウンターは常に空いている。奥＝ボード（既存の並列盤面）。

### 観測可能な完了条件（Expected Behavior）

- [ ] **G1（脱ブロック）**: タスクが走っている最中でも、ドックの入力欄は**開いたまま**。
  「動いています」表示中に次のオーダーを送れる（送信が即・受理される）。
- [ ] **G2（受付の非作業性）**: ドックに送ったオーダーは、受付自身が working に入らず、
  **後ろのワーカー run** としてキックされる。受付はすぐ次を受けられる。
- [ ] **G3（ライブ・ロスター）**: 走っているタスクの一覧が**クリック無しで常時見える**面がある
  （カンバンのカードと別。カードは"落ち着いたもの"、ロスターは"生きているもの"）。
- [ ] **G4（行の解剖）**: ロスターの各行が ①オーダー ②方向の脈 ③信号 を持つ（下記 §3）。
- [ ] **G5（方向の脈）**: 脈は**動作ステータスではなく意図/方向**。判断が変わったときに更新。
- [ ] **G6（操舵）**: 各行から **[止める] / [軌道修正]** ができる。
- [ ] **G7（仮定で進む）**: ワーカーは要件が曖昧でも止まらず、**妥当な仮定を置いて進み、
  🚩でフラグ**する（ハードな ✋要確認 は本当に進めないときだけ）。
- [ ] **G8**: `npm run build` / `tsc` / `lint` / `test` 緑。日本語 IME を壊さない。

## 2. なぜカードでなくロスターか

- **カード（カンバン）** ＝ *落ち着いたもの*の表現。静止して「こういう状態」と語る。
  クリックで開くのが正解（急がないから）。
- **走っているタスク** ＝ *生きているもの*。動いているのを感じたい、止まったらすぐ気づきたい、
  触りたいとき**ゼロクリック**で届きたい。**静止カードでは表現できない。**
- **タブは却下（主役としては）**: ユーザーの実ワークフローは「ターミナルを縦長にして
  2〜4枚*タイル*する」＝**全部を同時に見ていたい**。タブは1つだけ見せて他を隠す＝真逆。
  → ロスターは常時可視。見張りたい2〜4本だけ引き出して**タイル**。
  タブが要るのは走行数がタイル可能数を超えたときの**あふれ受け**だけ。

### ターミナル並列の本当の罪
「窓が多い」ではなく「**蒸留してくれない**」。生ログの洪水を、脳が4本同時にリアルタイム要約
する羽目になるのが大変だった。**OG が勝てる一点はここ**＝洪水を「アンカー＋脈」に蒸留する。
（CLAUDE.md「N窓を1キャンバスに畳む」の本当の意味＝窓ではなく*洪水*を畳む。）

## 3. 走行タスク1行の解剖図

```
┌─────────────────────────────────────────────┐
│ ▶ auth リファクタ              ← ① オーダー（不動のアンカー／何者か＋直近の指示）
│   「トークン期限を24hに」
│   → 方向: 既存セッションも一旦無効化して作り直す   ← ② 脈＝意図/方向（判断が変わったら更新）
│   🚩 仮定: ログイン中ユーザーは再ログイン必要      ← ③ 信号（🚩仮定 / ✋要確認 / ✓完）
│   [ 止める ]   [ 軌道修正 ]
└─────────────────────────────────────────────┘
        （クリックで生ログ全文＝掘りたいときだけ）
```

- **① オーダー**: そのタスクが何者か＋直近何を頼んだか。常時可視。**飛び込んだ瞬間に
  頭が再ロードされる**＝切り替えが速い。ターミナルが決して持たなかったもの。
- **② 方向の脈**: 「何をしているか（編集中…）」ではなく「**どっちに向かい、なぜそう判断したか**」。
  - 粒度は**ステップ単位だが、ステップ＝動作の節目ではなく*判断*の節目**。
    事故は決断で起きるので、決断が変わったときだけ一行更新＝静かなのに肝心は逃さない。
  - これは 🚩仮定フラグと**同じ素材**（仮定＝曖昧さの中の決断）。
- **③ 信号**: 動 / 🚩仮定を置いた / ✋手を挙げた（要確認） / ✓完。**隠さない。**
  「クリックして初めて気づく」を消す。気配は周辺視、精読は開いたときだけ。

## 4. 操舵のループ（双方向の ✋）

- エージェント → あなた: 「✋ 迷っています、どっち?」（向こうが手を挙げる）
- あなた → エージェント: 「✋ その方向は違う、こう直して」（**あなたが手を挙げる**）

後者を可能にするのが「**見える方向**」。見えない方向は止められないし直せない。
「やばかったら止める」は、方向が常に読めて初めて成立する。
要件確認は**カード自身**（盤面の中の線形会話）で行い、受付は混ませない。

## 5. 技術的な追い風

- claude 自身が plan / todo / 判断を喋っている（claude code は計画を出す）。
  **"方向"はもうストリームの中にある。** OG の仕事は「決断と理由の行を拾い、機械的ノイズを
  捨てる」蒸留＝*ステータスバーの真逆*。
- 既存資産: `useRuns.runTask(project, task, {resumeFrom})` / `allTaskRuns`（履歴）/
  SSE（live）/ worktree 隔離 / `BOARD_ADD:` マーカー。受付→ワーカーの分離は
  「ドックが run を*自分で抱えず*別タスクとして起こす」配線が主。

## 6. 決定事項（2026-06-07 確定）

1. **並列の引き金**: 引き金は無し＝受付が各オーダーを即レーン化（多オーダー並走は自動の結果）。
   **加えて「1発の自動分割」も既定オン**＝受付が1つの発言を複数レーンに割れる。
2. **新規オーダーの既定**: 新レーン。関連が強ければ受付が「○○に合流?」と推測提示し、
   ワンタップで走行中レーンへ合流（同branch・直列）。**レーン内＝直列／レーン間＝並列。**
   マージ衝突が起きるのはレーン間だけ＝ユーザーが独立だと宣言したものだけ。
3. **並走結果の戻し方**: ブランチのまま。ロスターに ✓＋[取り込む]。取り込みは**逐次＋衝突提示**。
   **自動マージはしない**（未レビューを main に自動投入は背骨に反する。正否の判定者はユーザー）。
4. **方向の蒸留**: `OPENGROUND_STEP: {方向, 理由, 仮定[]}` を worker が emit、parser が live で
   拾って ②脈＋③🚩 へ。`OPENGROUND_RESULT:` と同型の途中版。ヒューリスティックは fallback。

### 実装の段取り（壊さないための staging）

コード調査で判明した足場（2026-06-07）:
- `runTask` は毎回 fresh session を作れる＝**複数セッションは既にデータモデル上 OK**。
  「1会話」なのはドックが常に同じ assistant task を resume してるだけ。
- **同一プロジェクトの run はサーバ側で直列化**（runner の per-project ロック）。
  ＝複数レーンを投げても*同じ作業ツリーを2つの claude が同時に踏まない*。真の並列は
  worktree-per-lane が要る（レーン間＝別branch という §6-2 と一致）。
- 入力は既に `enqueueInstruction`/`pendingByTask` で「走行中でも次を積める」配線がある
  （ただし同じ会話に直列チェーン）。

段取り:
- **第1スライス（本PR）**: **読み取り専用のライブ・ロスター**＝走行中 run を常時可視化
  （`taskRuns`＋`data.tasks` から導出、実行ロジックに非接触＝daily-driver を壊さない）。
  → ユーザーが dogfood して feedback。
- **第2**: 受付の脱ブロック（新オーダー＝新レーンを spawn、入力は塞がない）。
- **第3**: 方向の脈（`OPENGROUND_STEP`）→ 自動分割 → worktree 並列 → 取り込みマージUI。

## 7. 設計の背骨（最初の1本の線）

```
受付（働かない・常に開く）         ← あなたを"待ち"にも"貯蔵庫"にもしない
   ↓ 伝票を流す
ライブ・ロスター（常時可視の帯）    ← オーダー＋方向の脈＋信号
   ↓ 方向が見える
操舵（止める / 軌道修正）          ← 意図が読めるから、手遅れ前に効く
```

## 9. ハンドオフ / dogfood

**ブランチ**: `feat/dispatch-full`（worktree `../og-dispatch-wt`、`main` 起点。`main`
チェックアウトは未変更）。マージはしていない — dogfood→feedback してから。

**触り方**（※ユーザー稼働中アプリと固定ポート 47776 が衝突するので、稼働中アプリを止めてから）:
```bash
cd ../og-dispatch-wt && npm run electron:dev   # or http://127.0.0.1:5174
```

**動作（期待される振る舞い）**:
- プロジェクトを開き、ドックでオーダー → 走る。**走行中**にドックでもう1つ送ると、その送信は
  **新レーン**として spawn され（ボタンは「別レーンで」）、画面下の**ロスター帯**にチップが出る。
  入力欄は塞がらない。idle 時の送信は従来どおりアシスタント会話を resume（単一会話は維持）。
- ロスターのチップ = **オーダー + → 方向の脈 + 🚩仮定 + 停止**。チップを押すとそのレーンを開く。
- 方向の脈は claude が `OPENGROUND_STEP` を吐いたときに出る（判断の節目ごと、ステータスではなく意図）。

**feedback で見てほしい点**:
1. ロスターの位置（最下部の帯）と粒度。タブ横断で常時見えるのは正解か。
2. 「走行中の送信＝新レーン」既定は直感に合うか（idle=resume / busy=lane の分岐）。
3. 方向の脈が実際に「役立つ意図」になっているか（claude の `OPENGROUND_STEP` 出力品質）。
4. 自動分割（§6-1）を本当に既定 ON にするか — 実装前に挙動を見て判断したい。
5. マージは現状「逐次自動＋衝突提示」のまま。「ブランチのまま＋[取り込む]」(§6-3) に
   変えるべきか（コア runner 変更なので feedback 必須）。

### 既知の軽微エッジ（夜間レビューで確認、feedback 後でよい）
- **ドック添付→レーン化のサムネイル帰属**: ドックで画像/ファイルを添付した状態で
  *走行中*に送る（＝レーン化）と、添付は instruction に**絶対パスで埋め込まれ**レーンの
  claude は問題なく Read できる（＝機能は正しい）。ただしサムネイルの保存先が新レーンでなく
  **アシスタントタスク**になる（`drainStagedIntoInstruction` の `onUpdate` 先がドック＝
  アシスタント task のため）。低 severity。修正は paneSubmit の drain 順序 / `onSpawnLane`
  署名にステージ画像を渡す形が要り挙動に触れるため保留。
- レビュー結論（②〜⑩ほか）: セキュリティ境界=迂回なし / SSE catch-up・rehydrate の脈再現=
  堅牢 / レーン生成の stale closure=実害なし。上記サムネイル帰属以外に未解決の不具合なし。
