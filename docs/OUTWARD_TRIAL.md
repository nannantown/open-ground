# OUTWARD TRIAL — 外部プロジェクト実戦投入の実験計画(判定条件を先に固定する)

**制定: 2026-08-12。実行者: オーナー(実機でのみ実行可能)。期間: エンジン ON 開始日から 4 週間。**

## 0. 目的 — 「これ意味ある？」をデータに変える

swarm はこれまで主に自分自身(OG リポ)を改良してきた。この実験は
**「swarm はオーナーの介入コストを下回るコストで、OG 以外の実プロジェクトに
検証済みの作業を着地させられるか」** を、事前に固定した判定条件で測る。

計測器は実装済み: Swarm タブ司令官ダッシュボードの **「着地 / 週」**
(`GET /api/swarm/kpi/landed` — 再起動を生き延びる永続台帳。正典は
`src/lib/server/swarmLandedLedger.ts`、経緯は docs/commander/00-INDEX の
2026-08-12 追記)。外部と OG 自身が分かれて出るので、この実験の主指標が
パネルでそのまま読める。

**この文書の掟: 判定条件は開始前にだけ動かせる。** 開始後に条件を動かしたく
なったら、それは「実験が失敗している」というデータであり、条件の欠陥ではない。
(調整したい場合は実験を中止 → 条件を書き直して仕切り直し — 途中変更はしない。)

## 1. 判定条件(開始前に数字を確定し、この表を埋めてから ON にする)

| # | 条件 | 既定値(根拠) | 開始前に確定した値 |
|---|---|---|---|
| A | **外向き着地** — 4 週合計で外部プロジェクトへの着地 ≥ N 件 | N = 8(2 件/週。プロジェクト 2〜3 個で「1 プロジェクトあたり隔週 1 枚」— 道具と呼ぶ最低線) | ______ |
| B | **介入効率** — 介入 1 回あたり着地 ≥ 1(介入 = escalation への回答 + 誤診/事故の尻拭い + 差し戻しの手動指示。**着地数 ≥ 介入数**) | 1.0(介入の方が多い道具は、道具ではなく世話) | ______ |
| C | **ハード条件** — 実データ破壊事故 0 件(worker の `npm test` がオーナー実データを壊す類 — 07 章の事故型) | 0(1 件でも即中止・不合格) | ______ |
| D | **主観条件** — 4 週目の終わりに「来月もこの運用を続けたいか」に即答で Yes | Yes/No(数字が良くても運用が苦痛なら道具として失敗) | ______ |

**判定(4 週後、三択):**

- **A・B・C・D すべて成立 → 合格。** swarm は道具として自活している。cockpit との統合体験
  (Ground カードから swarm の状態が見える等)へ投資を戻す。
- **A または B が不成立、だが期間中の事故が新しい教訓を生んだ(docs/commander に新しい
  原理が増えた)→ 研究として続行。** 名札を「生産性の道具」から「運用研究」に付け替え、
  corpus の外部化を主産物に昇格する。罪悪感なしで続けてよい — ただし名札は正直に。
- **A・B 不成立で、事故も既知の型の再発ばかり → 凍結。** swarm を止めて cockpit 製品に
  集中する。資産(docs/commander の corpus・信頼アーキテクチャ)は既に手元に残っている。

## 2. 準備(オーナーの実機・30 分)

1. **プロジェクト選定 — 2〜3 個。** 基準:
   - 実際に進めたい実プロジェクトであること(実験用のダミーは不可 — B が測れない)
   - git リポであること・`npm test` 相当の完了ゲートが回ること(ゲートが無いリポは
     worker の「効いた」が検証できず、掟 2 に反する)
   - **失って困る未コミット作業を残していない**こと(worker は worktree で隔離されるが、
     実験の心理的安全のため)
2. **登録**: Ground の「Import existing folder」で各プロジェクトを登録。
3. **玉込め**: 各プロジェクトの Board:todo に 5〜10 枚のカードを書く。書き方は
   `/order` の流儀(観測可能な完了条件・1 枚 = 1 worker が 90 分で届く粒度)。
   最初の玉の質が実験の質を決める — 曖昧な玉は escalation(= 介入)になって B を削る。
4. **介入ログの置き場を決める**: このファイルの §4 に日付+1 行で追記していく
   (介入のたびに書く。あとでまとめて思い出すのは必ず過少申告になる)。
5. **判定条件の表(§1)を埋める。** ここまでやってからエンジン ON。

## 3. 運用ルール(4 週間)

- エンジンは基本 ON のまま(§1-C の事故時のみ即 OFF)。quota 枯渇時の park は
  介入に数えない(自動回復する待ちは道具のコストではない)。
- **介入に数えるもの**: escalation への回答 / blocked カードの手動解決 /
  誤診の尻拭い(00-INDEX の症状表を引く作業を含む)/ 差し戻しの手動指示 /
  司令官卓への手動指示(「状況」の定期確認は数えない — 監視は介入ではない)。
- **数えないもの**: 玉込め(注文は仕事の依頼であってコストではない)/
  着地したコードのレビュー(それは A の品質側で、司令官の重量級レビューが担う)。
- 週次で 5 分: 「着地 / 週」パネルの外部系列と §4 の介入数を見比べ、B の暫定値を
  このファイルに追記(週 1 行)。

## 5. この実験がやらないこと

- **swarm の改良はしない**(期間中に見つかった欠陥は起票だけして、修理は OG カードへ。
  修理に飛びつくと「工場の生産量の半分が工場の修理」の再演になり、A が汚れる)。
  例外: §1-C 級の安全欠陥は即修理してよい(そのときは実験を仕切り直す)。
- 判定条件の途中変更(§0 の掟)。
- 「もう 1 週だけ延長」(延長したくなった = D が No というデータ)。
