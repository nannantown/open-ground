# TRUST KERNEL — 信頼カーネル仕様(OG 非依存で成立する部分の抽出)

**制定: 2026-08-12。** 対象読者: この設計を OG の外(別プロダクト・ライブラリ・仕様公開)へ
持ち出すとき、および swarm の安全層を改修する worker(何が「カーネル」で何が「配管」かの線引き)。

> **なぜこの文書があるか。** OG swarm の実装の大半(quota 五層・画面スクレイプ・PTY 管理)は
> プラットフォームの観測ギャップへの補償工事で、公式が埋めれば消える(PLATFORM-GAP-LEDGER)。
> 一方でここに書く「信頼カーネル」は逆の性質を持つ — **モデルが賢くなるほど委任は増え、
> この層の重要性は増す**。古びない部分を、古びる配管から仕様として分離しておく。

## 0. 中核原理(1 行ずつ)

1. **AI の遵法は安全装置ではない。** 禁止は「守られる規範」ではなく「存在しない経路」で
   実装する(CLAUDE.md 検証の掟 3 の含意を安全設計に一般化したもの)。
2. **判断はモデルへ、権力は構造へ、価値観は人間へ。** 三者を混ぜない。
3. **エスカレーションは自信ではなく可逆性で切る。** 確信があっても不可逆なら人間へ。
   不明は不可逆に倒す(fail-closed)。
4. **自己申告は宣言であって証明ではない。** 昇格・統合・完了の全ゲートは観測可能な
   証拠(コミット・読み戻し・実測)を要求する。
5. **安全装置は「外すと赤くなること」を実測してから信用する。** 発火しない番人は
   安心を配るだけの飾り(検証の掟 1)。

## 1. 権力分立(separation of powers)

| 役割 | 権限 | 権限の根拠 |
|---|---|---|
| worker(手) | 自分の隔離 worktree にコミットする。それ以外に何も動かせない | worktree 隔離 + guard hook + 完了ゲート |
| engine(神経系・反射) | 検知・配車・回収・蘇生。**trunk を動かす経路がコードに存在しない** | 「経路の不存在」を回帰テストでピン(manager-only regression) |
| manager(脳) | 重量級レビュー + 手動 FF push = **trunk を動かせる唯一のロール** | ただし高リスク force-hold / [hold] 規約 / fail-closed 0 票禁止に服する |
| overseer / proxy-you | worker の質問に「オーナーとして」答える。**可逆な範囲でのみ** | 可逆性ゲート(§2)+ 校正された棄権(§3) |
| 人間(オーナー) | 不可逆操作の全て + 政策層(モデル mask・self-supply 承認・release) | 恒久境界(TARGET-STATE §5 の表)— 到達目標ではなく**永続の線** |

**カーネルの不変条件 P1〜P4:**

- **P1**: 実行体(engine)と統合権(manager)は同一プロセス・同一ロールに同居しない。
- **P2**: 自己生成した作業(self-supply)は、生成者自身が実行をスケジュールできない
  (per-item の人間承認フラグが dispatch ゲートに入る)。
- **P3**: 不可逆操作の一覧は「恒久境界」として文書化され、自動化の到達目標に**永遠に**
  含まれない(境界の変更は人間の政策決定であって、技術的到達ではない)。
- **P4**: P1〜P3 は規約(プロンプト)ではなくコード(経路の不存在・ゲート・フラグ)で
  実装され、それぞれ「壊すと赤くなる」回帰テストを持つ。

## 2. 可逆性ゲート(reversibility gate)

正典実装: `src/lib/server/swarmReversibility.ts`(静的分類器)。

- **入力**: `{ kind: 'bash' | 'tool' | 'question', text }` — シェルコマンド / ツール呼び出し /
  自然言語、で適用する構造規則を切り替える。
- **出力**: `reversible | irreversible | unknown`。**unknown は irreversible と同じ扱い**
  (不明は不可逆に倒す)。
- **設計制約(移植時も維持すること)**:
  - **モデルを呼ばない**(判定ゲート自身が LLM を使うと、依存すべき唯一の軸が
    非決定的になる)。
  - **precision 優先**: 金銭/公開/削除/資格情報の各規則は必ず目的語か金額で限定する。
    裸の言及(「課金ボタンを追加して」)で発火する規則は、本物のエスカレーションへの
    信頼を侵食するので入れない。パラフレーズの検出は意味判定層(§3)の仕事。
  - **全パターンが有界**(ReDoS 対策 — 攻撃者管理の自由文を線形時間で分類できること。
    実測で quadratic を踏んだ前例が正典コードのコメントにある)。

## 3. 二層防御(semantic judge × structural backstop)

proxy-you(`swarmOverseerBrain.ts` の `answerAsOwner`)の形。**どちらの層も単独では信用しない**:

1. **前段ゲート**: 質問文を §2 の分類器に通す — 明白な不可逆は脳を呼ばずに人間へ。
2. **意味判定(脳)**: オーナーの判断軸 corpus **だけ**を根拠に、LLM が
   ANSWER / ESCALATE(不可逆)/ ABSTAIN(corpus が薄い — **校正された棄権**。
   捏造せず「分からない」と申告する)を出す。
3. **後段ゲート**: 脳の**回答文自体**をもう一度 §2 に通す — プロンプト注入で脳が
   不可逆指示を吐いても、構造層が握りつぶす。

**カーネルの不変条件 R1〜R3:**

- **R1**: 意味判定層の根拠は人間本人の corpus に限定する(worker の主張・外部文書を
  判断根拠に混ぜない — それらは「データ」であって判断軸ではない)。
- **R2**: 棄権は失敗ではなく正常出力(「corpus がこの領域を覆っていない」は、
  観測地図を育てる入力になる — 判断ルーティングの UNCLASSIFIED 質問)。
- **R3**: 判定層への入出力は両方向ゲートする(入力だけのゲートは、注入で汚染された
  出力を素通しする)。

## 4. 判断ルーティング(decision routing)

正典実装: `swarmDecisionRouting.ts`。宛先の正典は 2 つ**だけ**:
**関与の観測地図**(オーナーが実際に関与してきた領域の記録 — you-corpus)と
**恒久境界**(§1-P3)。カテゴリを発明しない。地図に無い領域は
「これはあなたが決めたい種類の話ですか?」を 1 問だけ聞き、その回答が地図を育てる。

- 移植時の要点: ルーティング表を静的に持つのではなく、**本人の行動記録から育てる**。
  誤配(技術詳細がオーナーへ / 好みの問題が専門家へ)はどちらも信頼を削るので、
  初期は「聞く」に倒してよい — 1 問が地図を 1 行育てる構造なら、聞く回数は単調減少する。

## 5. 検証の掟(カーネルに含まれる理由)

権力分立は「ゲートが実際に機能していること」に全面依存するので、検証規律は
信頼カーネルの一部である(独立した品質施策ではない):

- **V1**: ゲート・番人は「本番を壊して赤を実測」してから信用する(掟 1)。
- **V2**: 完了は観測可能な結果で判定する — 書いたら本番の読み手で読み戻す(掟 2)。
- **V3**: 生成者と検証者が同型の盲点を持つ前提で設計する(同じ LLM がコードもテストも
  書く環境では、緑は独立した証拠にならない — 構造・実測・変異で補強する)。
- **V4**: 同じ欠陥型が 2 回出たら、レビューではなく構造で止める(存在検査より過大近似)。

## 6. 抽出の現実(コードをどう切り出すか — 切り出さない、が答え)

- **ファイルは動かさない。** `swarmReversibility.ts` / `swarmDecisionRouting.ts` /
  `swarmOverseerBrain.ts` は `src/lib/server/swarm*.ts` グロブに**意図して**住んでいる —
  swarm-safety diff ゲート(`SWARM_CODE_PATHS` / `touchesSwarmPaths`)の適用対象で
  あり続けるため(正典コードの冒頭コメントが明記)。ライブラリ化するなら**コピー**して
  出す(この仕様書が仕様の正典、コードは参照実装)。
- 依存の現状: reversibility / decisionRouting は純粋(Node 標準のみ)。overseerBrain は
  PTY 起動・パス解決など OG 配管に依存 — 移植対象は `answerAsOwner` の**オーケストレー
  ション構造**(前段ゲート → injected runner → マーカー判定 → 後段ゲート)であって、
  runner 実装ではない。
- 公開するなら: この仕様 + 参照実装 2 ファイル(reversibility / decisionRouting)+
  §1 の不変条件テストの型、で 1 パッケージになる。それ以上(engine・quota・PTY)は
  カーネルではなく配管なので持ち出さない。

## 7. 採用チェックリスト(別システムがこのカーネルを名乗る条件)

- [ ] P1〜P4(権力分立が構造+回帰テスト)
- [ ] R1〜R3(二層防御・corpus 限定・両方向ゲート)
- [ ] 可逆性ゲートが静的・有界・precision 優先で、unknown が不可逆に倒れる
- [ ] 恒久境界の文書が存在し、自動化ロードマップから明示的に除外されている
- [ ] V1〜V4(番人の赤の実測記録がある)
