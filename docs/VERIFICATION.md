# 検証のやり方 — 「テストが緑」を「動く」の証拠にするために

> この文書は 2026-08-01〜02 の実測から書かれている。SDK ランタイム移行に対して
> **9周の敵対的レビュー**を回し、約60件の欠陥を直し、そのうえで**実機の受け入れ検証**を
> 5本通した。その両方の数字が残っているので、以下は方針ではなく**測って分かったこと**。

---

## 0. 一行で

**書いた人と確かめる人が同じなら、緑は証拠にならない。**
だから検証は「自分の判断に依存しない仕組み」の上に置く。

このリポジトリのコードもテストもレビューも、大半を同じ種類の LLM が書いている。
生成の盲点と検証の盲点は相関する（自分が書いたコードの修復が最も苦手 —
[arXiv 2606.30653](https://arxiv.org/pdf/2606.30653)／実装を正解としてテストを書くと
circularity of error — [arXiv 2507.06920](https://arxiv.org/html/2507.06920v2)）。
2026-08-01 の実測はこの通りだった:

- 棚卸し番人に**本番の欠陥を4件植えて、4件ともすり抜けた**
- `typeof rt[op] === 'function'` を見るテストは、**何もしない実装で満たされる**
  （停止・伝達・催促を全部空にしても76件が緑のまま）
- 同時起動のテスト2本が、**本物の SDK がクラッシュしきる前に数えて**緑になっていた
- コード内の「実測済み(0730)」が、**本番と違う入力形**で測ったものだった（因果が逆に書かれていた）

---

## 1. 番人は書くだけでは番人にならない — **必ず壊して赤を見る**

修正を入れたら回帰テストを書く。**そこで終わらない。**

```
1. 直す
2. 番人を書く
3. 本番コードを修正前に戻す      ← ここ
4. 番人が赤くなることを実測する    ← ここ
5. 復元して緑を確認する
```

3〜4 を飛ばしたテストは「守っているつもり」でしかない。
2026-08-01 は15件のコミットでこれを実施し、**そのたびに何かを掴んだ**。掴んだ例:

| 植えた欠陥 | 結果 |
|---|---|
| 排他ロックを外す | 22件が赤 |
| 唯一性判定から SDK プールを外す | 4件が赤 |
| 片付け中の卓を「居ない」と読む | 1件が赤 |
| 安全装置の書き込み範囲を壊す | 2件が赤 |
| 司令官が会話を忘れる | 2件が赤 |

**赤が出ないなら、その番人は消してよい。** 安心を供給するだけで検出しないものは正味マイナス。

## 2. 「呼べる」ではなく「効く」を見る

満たされてしまうアサーションの型（実測で確認済み）:

- `typeof f === 'function'` → 空実装で満たされる
- `expect(res.status).toBe(200)` → 書き込みが捨てられていても満たされる
  （`POST /api/settings` は allowlist で body を絞る。**本番の読み手で読み戻す**こと）
- 「エラーが出ない」 → 何もしていなくても満たされる

見るのは**観測可能な結果**。「関数が呼ばれた」ではなく「ディレクトリが残っている」「本文が
届いた」「プロセスが1本減った」。

## 3. fixture は**本番が実際に作れる形**にする

過去に踏んだ罠:

- `alive = () => ++calls < 3` — 本番ではありえない呼び出し回数依存
- worktree をリポジトリ**内**に作った（本番は repo 外の中央ディレクトリ）
- `{kind:'quota_refusal', raw:'API Error: 529'}` — 蒸留器が作れない組み合わせ。
  **本番が作れない入力に対する assertion が、誤ったゲートを正当化した**
- `path.resolve('C:\\wt')` を macOS で評価 — `path` は実行中の OS に固定される。
  **Windows のパス意味論はここでは再現できない**

疑わしいときは「この列は本番の CLI が実際に出すか」を一次資料で確かめる。

## 4. **実機の受け入れ検証**が、レビューでは出ないものを出す

9周のレビューでは出ず、実機で1発で出たもの:

- **配布ビルドで SDK worker が1体も起動しない**（`import.meta.url` が空になる。
  開発では100%動くので原理的に見えない）
- **Windows で安全装置が全書き込みを拒否**（`C:` のコロンで許可一覧が砕ける。
  両ランタイム共通・macOS のレビューでは永久に出ない）
- **戻すスイッチが実態と逆を表示**（出荷の直前に発見）
- **配布ビルドで SDK ランタイムが一度も点火していなかった**（0.11.47/0.11.48 の2版。
  CJS バンドルから ESM 専用の `sdk.mjs` を `require()` できず、毎回 PTY へ降格していた。
  **下の「実機」手順で回しても出ない** — §4.1 がその理由）

### いつ必ずやるか

**プロセス・git・ファイルシステム・claude のいずれかに触るものは、「できた」と言う前に
一度は本物で動かす。** 単体テストは全部その手前にある。

### やり方 — 第1段（この機体での実績手順）

```
1. アプリのデータだけ隔離: OPENGROUND_HOME=<一時ディレクトリ>
   ⚠ HOME は隔離できない（claude 本体と認証が実 HOME 依存。隔離すると 503 で止まる）
2. サーバを起こす: node server/dist/index.cjs
   ⚠ これは「本番と同じビルド」だが「本番と同じ実行環境」ではない（§4.1）
3. 捨てプロジェクトを登録して、本番の API 経由で操作する
4. 終わったら:
   - サーバ停止（ポート解放を確認。「停止した」ではなく解放を見る）
   - 実ホームに落ちた心拍を削除（~/.openground/swarm/ の差分だけ）
   - 実 settings.json が無傷か**キー単位で**確認
   - 残った claude / U 状態の git の本数を確認
```

## 4.1 `node server/dist/index.cjs` は**実機ではない**（2026-08-02 実測）

上の手順2は **同じバンドルを違う Node で動かしている**。本番は Electron が fork した
Node であって、`nvm` の Node ではない。**この差だけで結果が反転する**:

| | `require(ESM)` | 結果 |
|---|---|---|
| システム Node 22.22（手順2） | 許可される | **通る** |
| Electron 同梱 Node（本番） | 許可されない | **落ちる** |

これで 2 版（0.11.47 / 0.11.48）が「SDK ランタイム既定 ON」を謳ったまま、
**配布アプリでは1体も SDK が起動しない**状態で出荷された。降格は設計どおり働いたので
被害はなく、そして**だからこそ誰も気づかなかった**。

#### 実測値（2026-08-02、出荷済み .app 同梱の Electron + 同梱 SDK 0.3.220）

| 実行環境 | `require(ESM)` | `import(ESM)` |
|---|---|---|
| システム Node **22.22.0** | **OK** | OK |
| Electron **31.7.7**（= Node **20.18.0**、本番） | **FAIL**（`ERR_REQUIRE_ESM`） | **OK** |

**真因はビルド設定ではなく、走らせている Node の版そのもの。**
`require(esm)` が**既定で有効になったのは Node 20.19 / 22.12 以降**（それ以前は
`--experimental-require-module` が要る）。**Electron 31.7.7 が同梱するのは Node 20.18.0
で、20.19 / 22.12 のどちらにも満たない** — だから機能自体が効かず `ERR_REQUIRE_ESM` に
なる。**「Node 20 だからダメ」ではない**（同じ 20 系でも 20.19 以降なら通る）。同一の CJS
バンドル・同一の呼び出し形でも、**実行する Node の版だけで結果が反転する**（`import()`
は両方とも通るので、`require()` 側だけが罠になる）。

**再現コマンド**（インストール不要・GUI 非起動で再現できる — 出荷済み .app の Electron
バイナリをそのまま Node として使う。上の表はこの手順で取った）:

```bash
# worker 卓向けの注記: openground-guard.js は worker 限定で発動し、拒否するのは
# 「write roots（= 使い捨て worktree）の外」への書き込み。つまり worktree 内が許可側・
# /tmp が拒否側 — なので worker 卓ではこの一式を worktree 内の作業ディレクトリに置く
# （マネージャ/補習官/素の claude では guard 自体が no-op なので任意の場所でよいが、
#  repo を汚さない・後始末が楽という理由で worktree 内に置くのを既定にする）
mkdir -p .scratch/og-esm-probe && cd .scratch/og-esm-probe

# ⚠ probe.cjs 単体では解決できない。出荷 .app 同梱の node_modules を借りる（symlink）。
# ⚠ 2回目以降も同じコマンドを打つ運用が前提なので、必ず `-sfn`（force + no-dereference）
#   にする。素の `ln -s` は、node_modules が既にそのシンボリックリンクである状態で
#   もう一度打つと **リンクを辿って `.app` の node_modules の中に新しい symlink を
#   作ってしまう**（終了コード0・無警告。実測: /tmp で再現）。`.app` は `test -w` で
#   書込み可・署名済み（`codesign -dv` で hardened runtime を確認できる）なので、
#   これは出荷物への実害ある書き込みになる。
#   `-sfn` は既存リンクを辿らず「置き換える」ので、同じコマンドを何度打っても
#   `.app` 側は無傷（実測: 2回連続実行で `.app/.../node_modules` の中身が不変）。
ln -sfn "/Applications/OPEN GROUND.app/Contents/Resources/app/node_modules" node_modules

# probe.cjs — specifier は **bare** で書くこと（理由は下の ⚠）
cat <<'EOF' > probe.cjs
try {
  require('@anthropic-ai/claude-agent-sdk');
  console.log('require(ESM): OK');
} catch (e) {
  console.log('require(ESM): FAIL —', e.code || e.message);
}
import('@anthropic-ai/claude-agent-sdk')
  .then(() => console.log('import(ESM): OK'))
  .catch((e) => console.log('import(ESM): FAIL —', e.code || e.message));
EOF

# 本番側 — 出荷 .app 同梱の Electron を「Node として」動かす
ELECTRON_RUN_AS_NODE=1 "/Applications/OPEN GROUND.app/Contents/MacOS/OPEN GROUND" probe.cjs
#   → require(ESM): FAIL — ERR_REQUIRE_ESM
#     import(ESM): OK

# 対照 — システム Node（20.19 / 22.12 以降）で同じ probe.cjs
node probe.cjs
#   → require(ESM): OK
#     import(ESM): OK

# 表の版番号もこの場で取れる
ELECTRON_RUN_AS_NODE=1 "/Applications/OPEN GROUND.app/Contents/MacOS/OPEN GROUND" \
  -e "console.log(process.versions.node, process.versions.electron)"   # → 20.18.0 31.7.7

# 後始末 — symlink 本体と probe.cjs を消す。**symlink 側は `-r` を付けない・末尾
# スラッシュを付けない**こと。`rm -rf node_modules/`（末尾スラッシュ付き）は symlink
# を辿ってターゲット（`.app` の node_modules）の中身ごと消し、アプリが起動しなくなる
# （実測: /tmp で再現、ターゲットディレクトリそのものが消滅した）。`rm -f node_modules`
# （-r 無し・スラッシュ無し）なら symlink というファイル自体だけが消えてターゲットは
# 無傷（実測で確認）。差はスラッシュ1文字。⚠ probe.cjs も一緒に消さないと
# ディレクトリが空にならず、直後の `rmdir` が(黙って)失敗して `.scratch/` が
# working tree に残る（`|| true` は「rmdir が失敗しても後始末全体は止めない」ためだが、
# 消し残しがあれば rmdir 自体は失敗するので `git status --porcelain` で気づける）。
rm -f node_modules probe.cjs
cd - >/dev/null && rmdir .scratch/og-esm-probe .scratch 2>/dev/null || true
```

⚠ **specifier を `@anthropic-ai/claude-agent-sdk/sdk.mjs` と書くと、この手順は何も検証
しない。** このパッケージの `package.json` には `exports` マップがあり、公開されているのは
`.` / `./extract` / `./browser` / `./bridge` / `./sdk-tools` — **`./sdk.mjs` は非公開**。
`exports` を持つパッケージへの未公開サブパス require は **Node の版に関係なく**弾かれるので、
**両方とも `ERR_PACKAGE_PATH_NOT_EXPORTED` で FAIL** し、版差が消えて上の表と矛盾した
結論に着く（2026-08-03 実測。bare 版・サブパス版を両ランタイムで実行して確認）。
「検証手順が実は検証していない」の実例がこの章自身の中で起きた、ということ。

判定はコンソール出力の `OK` / `FAIL` を見るだけ（GUI は起動しない・読むだけの操作）。

⚠ **「第1段では原理的に再現できない」は正確ではない。** `node server/dist/index.cjs`
自体は特定の Node 版を強制しない — もしこの機体のシステム Node が Node 20.18 のような
`require(esm)` 未対応版なら、**第1段でも同じ `ERR_REQUIRE_ESM` が出る**（実際、リポジトリの
番人 `sdkEsmLoadFromCjsBundle.test.ts` は「開発機の Node + `--no-experimental-require-module`」
でこの分岐を第1段側で再現している。ただしこれは「Electron 31.7.7 が同梱する Node 20.18.0
そのもの」ではない — `docs/DISTRIBUTION.md` と `docs/commander/02-worker-lifecycle.md` が
"close, but not the Node 20.18" と整理している通り）。
※ これに対し「**dev(tsx/ESM) と vitest では原理的に再現しない**」は正しい主張のまま
（そちらは ESM 実行文脈なので `require()` の分岐自体が存在しない）。
正しい要点は版の有無ではなく**信頼性**: 第1段はシステム Node の版を誰も固定していない
ので、**たまたま緑（成功側）に倒れて見逃す**ことがある版依存の検査であり、実際
0.11.47/0.11.48 はこの検査で緑のまま出荷された。だから第2段（packaged `.app` での検証）
が省略不可になる。

### 第2段 — 配布形態でしか出ないものの検証（別枠・省略不可）

次のどれかに触ったら、**packaged `.app` を起動して**確かめる。第1段では原理的に出ない:

- **モジュールの読み込み方**（ESM/CJS 境界・`require` / `import()` / `createRequire`）
- **ネイティブモジュール**（node-pty など）・asar・`app.getPath` 系
- **`import.meta` / `__dirname` / `process.execPath` に依存する解決**
- **Agent SDK の起動そのもの**

```
1. npm run dist（または CI の成果物）を実際にインストールして起動する
2. 対象の経路を1回踏む（例: カードを1枚 dispatch する）
3. 判定は推測でなく記録から取る:
   curl -s "localhost:47776/api/swarm/orchestrator?path=<repo>" | grep -o 'runtime fallback[^"]*'
   → 降格していれば理由が全文で載る（これは設計どおり効いた）
4. SDK 卓かどうかの一番速い見分け: ps で `--remote-control` が付いていたら **PTY**
   （SDK 経路は remoteControl を意図的に外す — swarmManagerSdk.ts）
```

⚠ **未署名の自前ビルドをオーナー機で展開・実行しない**（macOS がマルウェア判定して
ゴミ箱に入れる実事故あり）。検証は**署名済みの配布物**で行う。

### ⚠ AI の遵法は安全装置ではない

禁止操作を指示すると、**AI が自分の判断で断ってしまう**。3回試して3回とも断られ、
装置は一度も作動しなかった。**断る理由のない普通の操作**で禁止規則に触れるもの
（例: `git checkout --` で未コミットを捨てる）を選んで初めて装置そのものが動いた。

「守られた」と「装置が働いた」は別物。受け入れ検証では必ず区別して記録する。

## 5. 同じ型が2回出たら、レビューをやめて**構造で止める**

9周で約60件のうち**15件以上が同じ1つの型**だった（2つの実装が併存しているのに片方だけを指す）。
毎周、**新しい呼び出し場所**で再発する。レビューは1件ずつしか殺せない。

### 判定の向きが生死を分ける

| 形 | 見落としたとき |
|---|---|
| **存在検査**（危ない箇所を登録させ、未登録なら落とす） | **沈黙** — リストの穴は何も言わない |
| **過大近似**（その名前がそもそも見えない） | **ビルドエラー** |

棚卸し番人（存在検査）は欠陥4件を植てて4件すり抜けた。
`no-restricted-imports`（過大近似）は、**まだ存在しないファイル**にも効く。

番人を作るときは「**見落としたらどちらに倒れるか**」を先に決める。

### 2026-08-04 の実測 — 同じ型が **3 回** 出た（許可リスト）と、**値の極性**という第2の型

**型①: クライアント側の手書き許可リスト。** サーバの union に新メンバーが増えても、
クライアントの `Set` に書き足さなければ**その行は黙って消える**。同じ型が3か所で起きていた:

| 場所 | 落としていたもの | いつから気づかれなかったか |
|---|---|---|
| `KNOWN_ANOMALY_KINDS` | `no-heartbeat` | 数か月（2026-07-14 に発見） |
| 同上 | `recover-review` | 4日後に**同じ型で再発** |
| `KNOWN_FATAL_EVENTS` | `guard-unwired` ほか3種 | 発見まで不明。**worker が1体も起動できない**通知が消えていたので、画面は「すべて静かです」と出ていた |

構造での止め方（今回採用）: **許可リストを撤去**して「空でなければ描画・未登録は生の名前」にし、
**ラベルの網羅だけ**を `types.ts` の union を**パースして**突き合わせる番人に持たせた
(`swarmOverseerFatalLabels.test.ts`)。落ちるのはテストで、**欠けている名前を本文に出す**。
⚠ パーサ自身が空振りすると番人が空になるので、**メンバー数の下限**と既知メンバー2つを
先に検査すること（この自己検査が無い棚卸し番人は「1件も見つからない＝合格」になる）。

**型②: エラー値と正常値が同じ値。** `countCommitsAhead` は「本当に0コミット」「trunk の ref が
解決しない」「git が失敗」を**全部 `0`** で返していた。読み手が2つあり、**極性が逆**だった:

- 昇格判定（`hasWork`）: 0 = 昇格しない → **無害**
- 回収判定（`recoveryColumn`）: 0 = **新しいブランチでやり直してよい** → commit 済みの作業が孤児化

`0` は片方の読み手にとって安全側、もう片方にとって**破壊側**。同じ関数の同じ戻り値でも、
**consumer ごとに「不明」の倒れる先を決めさせる**（`number | null` にして、null の扱いを
呼び出し側に書かせる）。tsc が全 consumer を名指しするので、**移行漏れが沈黙にならない**。

**見分け方（次に同じ型を疑うとき）**: 「この関数は**失敗を戻り値で表現しているか**?
表現しているなら、それは**他の正常値と区別できるか**?」— 区別できないなら、極性が逆の
2人目の読み手が現れた瞬間に破壊側へ倒れる。

## 6. 停止条件は「1周ゼロ」ではない

**「問題が出なくなるまでレビューを繰り返す」は到達できない。**

- レビューが見つける欠陥の**75%は可読性・構造**で、動作の欠陥は25%（Mäntylä & Lassenius, TSE 2009）
- 人数を1/2/4人、回数を1/2回に振っても**検出率に有意差なし**
  （Porter/Votta/Basili, TOSEM 1997・プロ11名/88インスペクション）
- 修正そのものの誤り率は**14.8〜24.4%**（Yin et al., FSE 2011）。
  1周5〜17件なら「毎周、修正が次の欠陥を作る」は**期待値どおり**

停止条件はこれ:

```
□ 型検査が緑
□ lint がエラー0（import 境界を含む）
□ 全テストが緑
□ ビルドが緑
□ 入れた番人すべてで、修正前の赤を実測した
□ プロセス/git/FS/claude に触るなら、実機で一度通した（§4 第1段）
□ モジュール読み込み/ネイティブ/SDK 起動に触るなら、**packaged .app で**一度通した（§4.1 第2段）
□ PII ガード・HOME 隔離ガード・棚卸し番人が緑
```

## 7. 効かないと実証で分かったもの（やらない）

- **レビューの周回を増やす**（§6）
- **カバレッジ目標**（Inozemtseva & Holmes, ICSE 2014「品質目標に使うべきでない」）
- **ミューテーションスコア(%)をゲート化**（Google が「行動に移せない」として破棄）
- **2実装に同じ入力を流して答えを比べる**（差分テスト）— この現場の欠陥は
  「答えが違った」ではなく「**片方しか数えなかった**」。比べる形は
  「一致したから安心」という**新しい偽の緑**を作る。必要なのは等価性ではなく**和集合**
- **変異テストの CI 常設** — テストが不定だとスコアが平均4ポイント振れ、9%が判定不能になる
  （Shi et al., ISSTA 2019）。**決定論化が先**

## 8. 不定に落ちるテストの診断

「別々のアサーションが不定に失敗する」は、**アサーションの問題ではないことが多い**。

実例（2026-08-01）: afterEach が**まだ書き込み中の一時ホーム**を消していた（`ENOTEMPTY`）。
エンジンのジャーナル追記は意図的に fire-and-forget なので、処理が返っても書き込みが残る。
vitest はその後片付けの失敗を**直前のテスト**に帰属させるので、2つの症状に見えていた。

- 再現手順: `node -e 'while(...)'` を6〜8本走らせて負荷をかけ、対象ファイルだけを繰り返す
- 一時ホームを消すなら `rm(dir,{recursive:true,force:true,maxRetries:10,retryDelay:50})`
- 関連: `docs/commander/07-test-isolation-contract.md`

## 9. 「実測済み」と書くときの規律

コメントに数値や因果を書くと、**それが根拠として引用される**。2026-08-01 に、
コード内の「実測(0730)」を根拠に因果が逆に書かれていた事例が出た。原因は
**本番と違う入力形で測っていた**こと。

- 測ったら、**測った構成**（何を入力にしたか）も書く
- できるなら、主張をコメントではなく**テスト名**に移す（テストが消えれば主張も消える）
- 「本番はこの形か？」を一次資料（型定義・実際の出力）で確かめてから書く
