# Ground の自動運用フレーム

Ground の通常のフレームを作り、その見出しにある「自動運用」スイッチで対象を設定する。複数のフレームを同時に ON にできる。左上の専用作成ボタンと、オーナー画面のプロジェクト別の自動運用ボタンは置かない。手動の社長・マネージャーとの会話や停止操作は維持する。

設定は `CanvasState.automation` の V2（`version: 2 / revision / enabled: true / frameIds`）に保存する。`frameIds` は ON にしたフレームの ID の一覧で、表示名では判定しない。新しく作ったフレームや複製したフレームは OFF。名前の変更は運用状態に影響しない。見出しと名前の編集欄はゴシック体を使う。

0.11.199 の V1（`version: 1 / enabled / frameId` と `groundRole: automation`）も読み取る。最初のスイッチ操作で既存の ON 状態と revision を維持して V2 へ移す。V2 を保存した後、古い V1 クライアントによる保存や設定の省略は拒否する。

設定がない環境は既存の運用を継続する。オーナーがフレームのスイッチを操作した時から、ON のフレーム内だけを自動運用の対象とし、外では新しい自動作業を受け付けない。アップデートだけで一般利用者の自動運用を変更しない。最後のフレームを OFF にしてもフレーム管理は続き、対象なしになる。削除・非表示のフレームは対象を与えず、他の ON フレームには影響しない。不正な設定は対象を空にし、既存運用へ暗黙には戻さない。

所属は保存済み位置を基準に、Ground が使うカードの中心（256 × 140）で判定する。フレームの回転も表示と同じ座標変換で扱う。移動・サイズ変更・再読み込み・HTTP 保存に同じ純粋関数を使う。入れ子や重なりがある場合、いずれかの ON フレームに入っていれば対象になる。名前だけが同じフレームに権限はない。一つのフレームを動かしても、別のフレーム内のカードは運ばない。

スイッチ、ON フレームの範囲・表示状態、所属を変更する保存には、サインイン済み owner と現行の revision が必要。子フレームの表示に関わる親グループもこの判定に含む。古い保存内容は 409 で拒否し、読み込み直す操作を表示する。保存失敗中の配置は自動作業へ反映しない。Canvas の通常保存、登録解除、削除、旧データの移行は共通の read/modify/write ロックを使い、フレーム設定を古い snapshot で上書きしない。

未保存の配置は編集時のアカウントと世代へ固定する。アカウント切り替え後は自動送信せず、古い ACK で新しい配置を消さない。元のアカウントへ戻って明示的に再試行するか、保存済みの配置を読み込む。読み込み待ち中の新しい編集も、古い読み込み操作では捨てない。

保存完了後、サーバーが既存の権限・作業モード・認証・利用枠・安全確認を通して自動運用を適用する。画面を開くこと自体を起動の契機にしない。対象外へ移しても受理済みの actor、成果、worktree、branch は削除せず、既存の監視を残す。新しい dispatch、統合指示、自動 wake は停止する。手動の社長会話は利用できる。フレーム管理中はプロジェクト側の自動運用スイッチ・開始・再開操作を表示しない。フレーム機能を使わない一般利用者の既存操作は維持する。

画面の手動操作は `/api/swarm/supply/open`、`/api/swarm/manager/open`、`/api/swarm/manager/input` を使う。役割間の自動プロトコルは従来の `/supply`、`/manager`、`/manager/say` を使い、フレームの対象外なら保留する。リクエスト本文で起動元を選ぶことはできない。

検証は一時 home、fake actor、ブラウザ内の API fixture のみで行う。通常アプリ、実プロジェクト、モデル、認証情報、課金 AI API は使用しない。

```sh
npx vitest run src/lib/automationFrame.test.ts src/lib/server/groundCanvas.test.ts src/lib/server/groundCanvasMutation.test.ts server/routes/__tests__/groundAutomation.test.ts
npx playwright test e2e/automation-frame.spec.ts
```

UI のブラウザテストは全 `/api` を遮断してメモリ内 fixture に置き換え、ライト・ダークで作成、カード移動、サイズ変更、再読み込みを確認する。エンジンの新規 admission と受理済み作業の監視はサーバーの専用回帰で確認する。

配布版 Electron 31.7.7 / Node 20.18.0 でも、実際の store・atomicWrite・
幾何判定・policy・orchestrator を一時環境に束ねて互換性を確認した。
認証と起動前検査は runtimeOwner / chatgptAccess / chatgptRuntime の3つだけを
明示的な fixture に置き換え、engine の actor 依存も fake とした。
ネットワークとユーザーディレクトリを OS 境界で拒否し、内 ON、外の新規配車ゼロ、
受理済み監視の継続、古い revision の拒否、削除・不正 policy の停止を確認した。
実ファイル・ディレクトリの fsync と 0600 を検証し、一時データは削除した。
これは実行環境と制御の検証であり、ベンダーへの実推論ではない。
